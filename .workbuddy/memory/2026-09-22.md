# 2026-09-22 工作日志

## 用户报「有bug」——实为 Redis 未启动 + 两处反馈缺失

**现象**：用户在 IDEA 重启了 8080（拿到新会话版代码）后尝试登录，反馈「有bug」。

**排查路径（值得复用的定位手法）**
1. 先看现场：`logs/` 有 1 分钟前刚写入的日志 → 应用刚跑过；6379 未监听、8080/8081 均无响应 → 进程已停。
2. 直接读 `logs/school-library-error.log` 而不是问用户 —— 立刻拿到 82 条 `RedisConnectionFailureException: Unable to connect to 127.0.0.1:6379`（Lettuce/netty `ConnectException: Connection refused`）。
3. 自起一个实例复现（`--server.port=8081 --app.library.scheduling-enabled=false`，**关定时器避免动真实库**），逐接口打，确定**爆炸半径**：
   - `/api/ping`、`/api/books`、`/api/announcements` 200 ✅（只读接口不碰会话）
   - `/api/loans/my` 无凭证 401 ✅（正常）
   - **`POST /api/auth/login` 500** ❌ —— 唯一坏掉的入口
   → 结论：**不是代码 bug，是 Redis 没起来**（登录要把会话写 Redis）。

**异常真实来源**：`SessionRepositoryFilter$SessionRepositoryResponseWrapper.onResponseCommitted` → `commitSession` → `RedisSessionRepository.save`。因为发生在「响应提交时」，异常沿过滤器链冒泡回 DispatcherServlet，**能被 `@RestControllerAdvice` 捕获**（这点很关键，决定了修法）。随后 Tomcat 转发 `/error` 又触发一次同样的 commit，形成 `Exception Processing [ErrorPage[errorCode=0, location=/error]]` 的二次刷屏。

**改了三处（都是真缺陷，不是凑数）**
1. `GlobalExceptionHandler`：新增 `@ExceptionHandler(RedisConnectionFailureException.class)` → **503 `SESSION_STORE_UNAVAILABLE`** +「会话服务不可用：无法连接 Redis（默认 127.0.0.1:6379），请先启动 Redis 再登录」。原来落兜底 500「服务器内部错误」，使用者完全无法定位。
2. 新增 `config/SessionStoreStartupCheck`（`ApplicationRunner`）：启动时 ping 一次 Redis，通 → INFO，不通 → **ERROR**（同时写进 `logs/school-library-error.log`）并附「怎么启动/怎么验证」的命令；**探测失败不阻止启动**（书目检索等应仍可用）。
3. `SecurityConfig`：`/error` 加进 permitAll —— 错误页不该要求登录，否则真错误会被二次拦成 401。
4. 前端 `views/LoginView.vue`：`catch` 里原来只有 `console.error('登录失败:', error)`，**界面上毫无反馈**（全项目 70 多处都用 `ElMessage.error(errorMessage(err, ...))`，只有这一处漏了）→ 用户点「登录」等于「点了没反应」。改为 `ElMessage.error(errorMessage(error, '登录失败，请稍后重试'))`。密码错误（400 BAD_CREDENTIALS）也因此第一次能正常显示「账号或密码错误」。
